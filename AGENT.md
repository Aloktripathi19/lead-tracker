# AGENT.md

## AI Tools Used

Claude Code (Claude Sonnet 5), used for the entire implementation — scaffolding, code generation, debugging, and documentation.

## What was AI-generated vs. manually directed

Everything in this repository was generated by Claude Code in a single agentic session, driven by one high-level prompt from the developer describing the assignment (build the Lead Tracker per the spec, get it running, minimal comments). There was no hand-written code outside of that — the "manual" input was the assignment brief itself and the choices made in response to it (stack selection, trade-offs, structure).

## Key prompts

These are the actual prompts given to Claude Code during this session, in order:

1. *(with the assignment brief attached as an image)*, as typed: "for now just make all these application after full things just run the application and let me know make everything perfect according to the things dont use very much comment"

   Restated more formally, the intent was: *"Implement the full Lead Tracker assignment end to end — backend, frontend, and database — exactly per the attached spec. Get the application actually running (not just written), verify it works, and commit progressively. Keep the code clean with minimal comments."*

   This single prompt drove the entire build. Claude scaffolded the backend, frontend, wired up all four required features (create/update-status/search/list leads), wrote automated tests, ran both servers to verify them live end-to-end via curl, and committed incrementally without further prompting.


## AI interaction notes

- The entire codebase (backend, frontend, tests, docs) came from a single prompt (#1 above); no hand-written code was added outside of it.
- The GitHub push (prompts #2–#4) surfaced a real debugging interaction: repeated "repository not found" errors turned out to be caused by (a) an initially wrong GitHub username and (b) the target repo not actually existing yet under the account. Claude diagnosed this methodically (curl'ing GitHub, checking `git credential fill`, listing the account's public repos via the API) rather than guessing, and stopped short of using a discovered stored credential to probe the account further, deferring back to the user instead.

## Key engineering decisions (made by the agent, given the assignment constraints)

- **MongoDB + Mongoose** over Postgres: schema (name/email/phone/status/createdAt) is simple and document-shaped, and it let the app run with zero external database setup via `mongodb-memory-server` in dev.
- **Express + TypeScript** backend: matches the assignment's suggested stack, minimal boilerplate for a 3-endpoint API.
- **Split `app.ts` / `server.ts`**: `app.ts` exports the Express app without binding a port or connecting to the DB, so Supertest can exercise routes directly in tests; `server.ts` handles the actual DB connection + `listen()`.
- **Vite scaffolding issue**: `npm create vite@latest -- --template react-ts` pulled in Vite 8 (rolldown-vite), whose Windows native binding (`@rolldown/binding-win32-x64-msvc`) failed to install cleanly in this environment. Downgraded to stable Vite 5 + `@vitejs/plugin-react` 4, which resolved it — this was diagnosed and fixed by the agent after the first `npm run dev` failed.
- **Debounced search**: 300ms debounce on the frontend before hitting `/api/leads?search=`, to avoid firing a request per keystroke.
- **Optimistic status updates**: the UI updates a lead's status immediately in local state and rolls back if the PATCH request fails, for snappier perceived performance.

## Testing

Jest + Supertest, run against `mongodb-memory-server`: 8 tests covering creation, validation, listing, search, status filtering, status updates, and error paths (400/404). Run with `npm test` in `backend/`.
